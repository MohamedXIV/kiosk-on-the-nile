## Message and recipe semantics

Social declarations add `message:{stage,thread,subject,sender,recipient,courier}`. Stages are request/reply/delivered; all three actors must differ. Requests and deliveries need explicit manual input, replies need the correct recipient. Memory retains the exact predecessor event ID and rejects missing, future, repeated or retargeted stages. Policies query typed `message.stage`. Sender/courier consent is scoped to the exact thread; replies grant scoped return permission. Latest refusal/retraction/expiry blocks future action. The two shipped threads are deliberately finite authored instances; new requests need new authored instance bindings.

Typed `message` assertions separately establish who actually knows each stage: player hears sender request; recipient hears the player's explicit question; player hears reply; original sender hears explicit delivery. Knowing a reply as courier does not reveal it to the sender before delivery. No message means the workshop actually happened.

Recipe connection is heard from the teacher before asking. Farid alone receives the authored initial `recipe_basics(shawarma)` seed, grounded in the existing relative/shop story; no NPC knowledge is inferred from player facts. Teaching relays that source to the student. Current continuation does not rerun its consumed start predicate. Attempt/result queries use RecipeLearning, which verifies actual workflow transactions. A result binding `query:recipe.latest_result,recipe:<ID>` captures a stable item identity at start; current/paused episodes keep that identity, while new starts select the latest real result. Recipes include declared learning-family IDs as well as workflow IDs. `knowledge_age` measures calendar boundaries from an actually heard/relayed assertion, not idle relationship score.
